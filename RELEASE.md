# Releasing TELOS

TELOS follows [Semantic Versioning](https://semver.org/): `MAJOR.MINOR.PATCH`.

- **MAJOR** — an axiom change, a blocked public interface change, or a
  capability-score *regression* that changes the system's contract.
- **MINOR** — a new capability dimension or a new governed channel (backward
  compatible).
- **PATCH** — fixes, docs, and internal changes with no contract change.

The version lives in exactly two places and they must agree:

1. `pyproject.toml` → `[project] version`
2. `telos/__init__.py` → `__version__`

`tests/core/test_version.py` locks the two together, so a release bump that
touches only one file fails CI.

## Release checklist

```bash
# 0. Clean tree, up to date with main
git status --porcelain && git pull --ff-only

# 1. Full release gate (suite + invariants + capability gates)
make check

# 2. Bump BOTH version sites and add a CHANGELOG entry
#    pyproject.toml  +  telos/__init__.py  +  CHANGELOG.md

# 3. Verify the version lock and the packaging smoke
python -m pytest tests/core/test_version.py -q
pip install -e . && telos --version

# 4. Commit, tag, push
git add pyproject.toml telos/__init__.py CHANGELOG.md
git commit -m "release: vX.Y.Z"
git tag -a vX.Y.Z -m "TELOS CogOS vX.Y.Z"
git push origin main --follow-tags
```

## Capability scorecard

Every release records the capability scorecard in the changelog entry
(`telos/audit/capability_scorecard.json` is regenerated by `make capabilities`).
A release that lowers a dimension without saying so in the changelog is a
release defect — the score is part of the artifact.

## What a release does NOT claim

- Maturity/adoption is capped at 4.0 until an *external* party reproduces a
  result (see `TELOS_V7.md` for the frozen-kernel boundary). A version tag is
  not adoption.
- The scorecard is self-measured. It is evidence of internal consistency, not
  independent validation.
